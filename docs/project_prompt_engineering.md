## 12. Engineering Standards (how to build it)

> Sections 1–11 say **what** the app does. This section says **how** to build it. It is just as binding. If a
> requirement above conflicts with a rule here (for example, storing credentials on the device), don't drop either
> one silently. Implement the safest version that still meets the requirement and record the trade-off in
> `docs/decisions/`.

### 12.1 Working rules for the agent

- **Plan before code.** Before the first line of code, write `docs/ARCHITECTURE.md`: components, data model, the
  encryption/key flow (§3), the role × endpoint permission matrix (§2), and the chosen stack with reasons. Keep it up
  to date.
- **Small, reviewable steps.** Build one feature slice at a time (backend + UI + tests), in the order of §11. Each
  slice ends green: build, lint and tests pass.
- **Don't break tested behaviour** (golden rule 3). Before changing a feature, run its tests. A bug fix starts with a
  failing test that reproduces it.
- **Ask before:** adding a runtime dependency, changing the encryption or key-wrapping scheme, changing the auth
  flow, or making a DB migration that is destructive or rewrites data.
- **Never claim something works without running it.** Report failing tests and skipped steps plainly.
- Keep an `AGENTS.md` (or `CLAUDE.md`) at the root with the build/test/run commands, conventions and known pitfalls.
  Update it when any of these change.

### 12.2 Repository layout

One repo (monorepo) with clear boundaries, for example:

```
/server            backend (API, auth, crypto, scheduler)
/web               frontend (built into static assets)
/android           WebView wrapper (Gradle project), only if the fallback in §9.2 is needed
/db/migrations     versioned, ordered schema migrations
/deploy            compose files, reverse-proxy config, systemd units
/scripts           dev/ops helpers (seed, backup, restore, key rotation)
/docs              ARCHITECTURE.md, decisions/ (ADRs), RUNBOOK.md, SECURITY.md, PRIVACY.md
/.github/workflows CI/CD pipelines (or the equivalent for the chosen CI)
.env.example       every config variable, with dummy values and a comment each
README.md          what it is, quick start, how to run tests
```

- Put crypto, authorisation, and the count/auto-submit logic in their own modules with no UI or HTTP code, so they can
  be unit-tested directly.
- The frontend has one source of strings (the translation table, §10.7). Never hard-code UI text.
- Pin toolchain versions (language runtime, Node; Gradle/JDK and Android SDK if §9.2 is built) in files the CI reads too
  (`.tool-versions`, `.nvmrc`, `go.mod`, Gradle wrapper, …).
- Commit lockfiles. Pin container base images to an exact version, not `latest`.

### 12.3 Secrets and configuration

- **No secret ever enters git**, including in tests, seeds, docs, examples, or commit history. Secrets here
  include: the server-held diary and profile keys (§3), session signing keys, the cron Bearer secret (§7.3), the
  translation API key (§8), DB passwords, TOTP secrets, and (if §9.2 is built) the Android signing keystore and its
  passwords.
- All configuration comes from environment variables or mounted secret files, following 12-factor. `.env.example`
  lists every variable with dummy values; `.env`, `*.keystore`, `*.jks`, `*.pem`, and `secrets/` are in `.gitignore`.
- The server **refuses to start** in production if a required secret is missing, empty, or a known dummy value. It
  logs which variable is wrong, never its value.
- Dev and test use separate, generated throwaway keys (for example, generated by `scripts/dev-setup`), never the
  production ones.
- Add a secret scanner (for example gitleaks) as a pre-commit hook **and** a CI step that fails the build.
- **Key custody is part of the design.** Losing the server-held diary key means losing every diary. Document in `docs/RUNBOOK.md` how it is generated, backed up (offline, separate from DB
  backups), and rotated (re-wrap all DEKs), and give the rotation a script and a test.

### 12.4 Security baseline

- **Authorisation is enforced on the server, per endpoint, against the role matrix.** Hiding a button is not
  authorisation. Default deny.
- **SYS_ADMIN must never receive plaintext content or comments.** Enforce this in the API layer: those code paths
  never call decrypt. Add tests that call every endpoint as SYS_ADMIN and assert that no response contains
  plaintext from a seeded diary.
- Crypto: use the platform's vetted library (no hand-rolled primitives). Use a unique random nonce per
  AES-GCM encryption, and bind each ciphertext to its record with associated data. Store password hashes with
  argon2id, with parameters at or above the current OWASP recommendation. Only the diary module may load the
  diary key; SYS_ADMIN code paths must not be able to reach it.
- SYS_ADMIN logins require a second factor (TOTP).
- Sessions use HttpOnly, Secure, SameSite cookies or short-lived tokens. Protect state-changing requests against
  CSRF. Sign out the user's other sessions on password change, and all sessions on admin reset.
- **Sanitise rich-text HTML on the server** with an allowlist (the editor's tags and attributes only) before storing
  and before rendering. Shared ("Open") diaries are shown to other users, so stored XSS is a real risk. Set a
  Content-Security-Policy.
- Validate all input on the server (including the 1–1080 clamp, image size limits, and request body size). Client
  validation is UX only.
- Use parameterised queries only. Rate-limit login, registration, forgot-password, and translation (cost control).
- The internal cron endpoint compares the Bearer secret in constant time and is not reachable through the public
  proxy if self-hosted.
- Never store passwords on devices. "Remember this device" is a long-lived, revocable server session.
- The service worker caches the app shell only, never API responses or diary content.
- Android (only if §9.2 is built): download self-updates over HTTPS only, and verify the APK (signature matches the
  installed app, plus a published SHA-256) before installing.
- No third-party CDN or Google-hosted assets (fonts, scripts, captcha); bundle everything. Users are in mainland
  China.
- Dependency audit (`npm audit`, `govulncheck`, `pip-audit`, Gradle dependency check, …) runs in CI. Keep
  `docs/SECURITY.md` with the threat model in a few paragraphs: who can read what, and what an operator with
  server/DB access can and cannot do.

### 12.5 Testing

- **Tests ship with the code in the same change.** No feature is done without them.
- Layers:
  1. **Unit:** crypto (round-trip, wrong key fails, tampered ciphertext fails, nonce uniqueness, ciphertext moved
     to another record fails), key rotation re-wrap, the permission policy (every role × action, including leaders
     never seeing unsubmitted drafts), history cap of 3, the sharing state machine, count clamping/trimming, the
     02:00 Beijing scheduler (inject a clock; never sleep in tests), and image downscaling decisions.
  2. **Integration:** the HTTP API against a real database of the production type (in a container), migrations
     applied from scratch. Cover every row of the role × endpoint matrix, both allowed and denied.
  3. **End-to-end:** a headless browser (for example Playwright) runs the §11 acceptance checklist against the
     running stack, in both languages, at a phone-sized viewport.
  4. **Installable app:** e2e checks that the manifest and service worker install, the app shell works offline, API
     responses are never cached, and a new deploy triggers the update toast. If §9.2 is built: unit tests for the
     updater/version logic and an instrumented smoke test.
- Tests are deterministic and isolated: injectable clock and RNG, a fresh DB per test (or per suite with rollback),
  no network to real third-party APIs (fake the translation API).
- Add a regression test for every bug fixed.
- Coverage is reported in CI. Aim for high coverage on crypto, authorisation, and counting; don't chase a global
  number with trivial tests.

### 12.6 Database and migrations

- Make schema changes only through versioned migration files that run automatically at startup or in a
  deploy step. Never edit a migration that has already shipped; add a new one.
- Migrations that touch encrypted data (re-wrapping, rotation) are idempotent, resumable, and tested on a copy of
  seeded data.
- Seed data (§11) is **dev/test only**, behind an explicit command or flag. It must never run against production,
  and seeded passwords and keys are not real ones.
- Backups: a documented, scripted backup **and a tested restore**. Encrypt backups. Remember that backups contain
  wrapped DEKs, so the diary and profile keys must be stored separately.

### 12.7 Debugging and observability

- Write **structured logs** (JSON in production, readable in dev) with a level, a timestamp, and a **request ID**
  that is passed to the client in a response header and shown in error toasts ("error ref: abc123"). A user report
  can then be matched to a log line.
- **Never log** passwords, tokens, keys, DEKs, diary content, comments, profile fields, or full request bodies.
  Log usernames and document IDs only. Write a test that greps captured logs for seeded plaintext.
- `GET /healthz` (process up) and `GET /readyz` (DB reachable, migrations current, secrets loaded). The Android
  fallback's Test Connection (§9.2) can use one of them.
- Log every auto-submit job run (start, users processed, entries written, failures), and keep an admin-visible
  "last run" status. A failed run must be noticeable, not silent.
- Errors return a consistent JSON shape (`{code, message, requestId}`) with no stack traces to clients. Stack traces
  go to the server log.
- A one-command local stack (`docker compose up` or `make dev`) with seed data, plus documented debug flags
  (verbose logging, SQL logging in dev only). The frontend has source maps in dev. If §9.2 is built, its debug build allows
  WebView remote debugging (`chrome://inspect`); the release build does not.
- `docs/RUNBOOK.md` covers: how to deploy, roll back, restore a backup, rotate keys, re-run a missed auto-submit,
  and where the logs are.

### 12.8 CI/CD

- **CI runs on every push and pull request** and must pass before merging to `main`:
  format check → lint → type check → unit tests → integration tests (with a DB service container) → build web →
  build server image → (build debug APK, if §9.2 is built) → e2e tests against the built stack → secret scan →
  dependency audit.
- The build is reproducible: the same commit gives the same artifacts. Build artifacts are not committed.
- **Releases come from tags.** A tag builds the versioned server image (including the web build). If §9.2 is
  built, the tag also builds the signed release APK: signing keys come from CI secrets and are never on disk in the
  repo, the APK version is the build timestamp, and the release publishes the APK, its SHA-256, and the version JSON
  together.
- **Deploys** pull the tagged image, run migrations, check `/readyz`, and can be rolled back to the previous tag
  by one documented command. Take a DB backup before any migration in production.
- Use separate environments (at least dev and prod; staging if possible) with separate secrets and databases.
- `main` is always deployable. Work on short-lived branches. Use Conventional Commits (`feat:`, `fix:`, …) so the
  changelog can be generated.

### 12.9 Code quality

- Use the ecosystem's standard formatter and linter, enforced in CI and in a pre-commit hook. Keep warnings at zero.
- Use static types where available (TypeScript in strict mode for the frontend; a typed backend language or full
  type hints).
- Prefer clear names and small functions. Comment *why*, not *what*. Public modules and functions get doc comments.
- Wrap errors with context, and never swallow them. Fail loudly at startup, and degrade gracefully at runtime (for
  example, translation times out → 504 and a toast, and the rest of the page keeps working).
- Accessibility: labelled inputs, keyboard-usable controls, sufficient contrast, and layouts that work on a
  360 px-wide phone.

### 12.10 Definition of done (per feature)

A feature is done only when **all** of these are true:

1. It meets its section of this spec and its §11 checklist items.
2. Unit, integration and (where it has UI) e2e tests are written and pass in CI.
3. Permission tests cover each role, both allowed and denied.
4. All new strings are in both languages.
5. No secrets, no plaintext in logs, and no new lint warnings.
6. Docs (`README`, `ARCHITECTURE`, `RUNBOOK`, `AGENTS.md`, `.env.example`) are updated if behaviour, config or
   commands changed.
7. A migration is added if the schema changed, and it was tested from an empty DB and from the previous version.
